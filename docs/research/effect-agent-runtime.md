# Optional agent application layer: Effect runtime research

Researched **2026-11-06** against official documentation, repository source, and npm manifests. Assessment only; no implementation. Upstream examples were inspected, **not executed or compiled in this starter**. No further delegation or independent reviewer was used, per the research brief.

## Recommendation and starter fit

Keep the base starter provider-neutral. Offer a separate, opt-in application example with **one bounded agent workflow, one model provider, one harmless tool, and one durable approval wait**. Start with one worker and the existing Postgres; use SQLite only for a deliberately local variant. Avoid introducing a generic agent framework before an application needs one.

The checkout already uses `effect`, `@effect/platform-node`, and `@effect/sql-pg` **4.1.2** through `pnpm-workspace.yaml`. `apps/api/src/main.ts` owns execution through `NodeRuntime.runMain`; HTTP handlers return Effects; `db/client.ts` exposes a narrow `Database` module and privately supplies `PgClient`. There is currently no agent loop, durable engine, worker, or deployment provider. A worker needs its own SQL layer: `DrizzleLive` does not export its internal SQL client. Prefer a shared internal SQL-layer composition if both apps eventually share the process; do not make workflow storage a responsibility of `Database.selectUsers`. Inspected: [README](../../README.md), [manifest](../../apps/api/package.json), [entrypoint](../../apps/api/src/main.ts), [HTTP](../../apps/api/src/http.ts), [database](../../apps/api/src/db/client.ts).

## Current APIs and maturity

- **Effect v4 is released; these subsystems remain unstable.** Official docs and current source identify **4.1.2**, while workflow, cluster, and AI modules carry `unstable`/`@stability unstable`. Current imports are `effect/workflow`, `effect/cluster`, `effect/persistence`, and `effect/ai`. Older `@effect/workflow`, `@effect/cluster`, `@effect/ai`, and `effect/unstable/*` snippets are version-specific; do not paste them into this starter. Sources: [4.1.2 manifest](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/package.json), [current workflow reference](https://effect.website/docs/v4/api/effect/workflow/WorkflowEngine), [older beta source tree](https://github.com/Effect-TS/effect-smol/tree/main/packages/effect/src/unstable).
- **Workflow primitives:** `Workflow.make` declares schemas and an idempotency key; `toLayer` registers the handler; `execute(payload, { discard: true })` returns an execution ID; `poll`, `interrupt`, and `resume` operate on it. `Activity.make` records named, schema-encoded results. `DurableDeferred` supplies external waits; `DurableClock` supplies persisted timers. `WorkflowEngine.layerMemory` is useful for tests, **not restart durability**. Sources: [Workflow](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/workflow/Workflow.ts), [DurableDeferred](https://effect.website/docs/v4/api/effect/workflow/DurableDeferred), [DurableClock](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/workflow/DurableClock.ts).
- **Durable engine:** `ClusterWorkflowEngine.layer` uses cluster sharding and message storage, and registers clock entities. `SqlMessageStorage` persists mailbox envelopes/replies, deduplicates request keys, and supplies migrations; `SqlRunnerStorage` handles runner/shard coordination. There is no need to build a custom engine for this example. Sources: [engine](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/cluster/ClusterWorkflowEngine.ts), [message storage](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/cluster/SqlMessageStorage.ts), [runner storage](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/cluster/SqlRunnerStorage.ts).
- **Persistence is a separate capability:** `Persistence` stores keyed results over memory, SQL, KVS, or other backing implementations. `Chat.layerPersisted` saves conversation history through it. Saving history does not schedule unfinished work or make an external tool call crash-safe. Sources: [Persistence](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/persistence/Persistence.ts), [Chat persistence implementation](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/ai/Chat.ts).

## SQLite versus shared Postgres

| Choice                           | Concrete composition                                                                                                                  | Guarantees and costs                                                                                                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Local, one process               | `ClusterWorkflowEngine.layer` over `SingleRunner.layer`, a file-backed `@effect/sql-sqlite-node` client, and `NodeCrypto.layerDigest` | Mailbox/activity results survive reopening the same file. Requires persistent disk and an owner process to resume work; no machine-failure availability by itself. Good embedded demo.           |
| One worker, Postgres             | Same single-runner composition over existing `@effect/sql-pg`                                                                         | Smallest fit here; durable state can outlive a worker host. Still **one active process** for this composition. Backups, retention, migrations, and worker supervision remain operational work.   |
| Several workers, shared Postgres | Actual cluster runner transport, sharding, SQL message/runner storage, health and lock configuration                                  | Supports ownership transfer and shared workers; adds network, lock/session, deployment, and failure-recovery concerns. PostgreSQL alone does not turn `SingleRunner` into a distributed runtime. |

`SingleRunner` uses no-op runner communication and health. Its messages are **always SQL-backed**, even with `runnerStorage: "memory"`; that setting does not mean ephemeral workflow history. Sources: [SingleRunner source](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/cluster/SingleRunner.ts), [SQLite client](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/sql/sqlite-node/src/SqliteClient.ts), [multi-runner harness and lock caveats](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/platform/node/test/cluster-integration/README.md). The local-disk and operational implications above are design judgments, not stronger upstream availability promises.

## Correctness rules for an agent loop

1. **Cancellation and recovery differ.** Fiber interruption and scoped resource cleanup govern a live process. A crash executes no finalizers. Persisted workflow messages and results enable later recovery; another owner must actually run the engine. An HTTP disconnect should stop the request's wait without accidentally cancelling an admitted run. Make user cancellation an explicit command. The official cluster tests separately cover restart, persisted interruption, owner handoff, and compensation; do not infer these from ordinary `Effect.fork` behavior. [Integration contracts](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/platform/node/test/cluster-integration/Workflow.test.ts).
2. **Completed activities are memoized, not arbitrary external effects exactly once.** A crash after a payment/email/tool succeeds but before its result is committed can repeat it. Activities that suspend internally can rerun their bodies too. Give each model turn and tool invocation a stable identity, isolate external calls in separate activities, and avoid enclosing a whole agent loop in one activity. Store model outputs before executing their requested tools. Keep budgets and limits explicit. [Activity implementation and suspension warning](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/workflow/Activity.ts).
3. **Retries require a side-effect policy.** `Activity.retry` advances `CurrentAttempt`; `Activity.idempotencyKey(name)` derives a stable execution-scoped key, optionally including the attempt. For a single business operation, normally keep the external deduplication key stable across attempts. Use provider idempotency or a transactional ledger/outbox and reconciliation for ambiguous results. Recording “done” before an external call can lose the action; recording it afterward can duplicate it. Compensation is another fallible action, not a transaction rollback. These recommendations follow from the crash window; the helper does not enforce them. [Activity retry/key source](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/workflow/Activity.ts).
4. **Approval is persisted input, not an open Promise.** Save the exact proposal/tool arguments, suspend on a uniquely named `DurableDeferred`, then complete it from a human decision. Bind approval to run, action identity, and proposal version; reject stale/repeated conflicting decisions; define rejection, expiry, and cancellation. Authentication/audit are application work. Deferred tokens identify the workflow, execution, and wait; they are not an authorization system. [Deferred source](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/workflow/DurableDeferred.ts).
5. **Replay and upgrades need a policy.** Keep workflow/activity names and serialized schemas compatible with outstanding runs; introduce a new workflow version for incompatible changes. Put changing model results/time/random decisions behind persisted steps. Set history retention and sensitive-payload policy. This is a recommended operating discipline; no automatic arbitrary-code migration guarantee was established.

## Effect AI: useful tools, not a complete durable harness

`LanguageModel` provides text/structured generation and streaming; `Tool` and `Toolkit` provide schema-based tool definitions and Effect handlers; `Chat` manages history and optional persistence. `McpClient`/`McpServer` are available if an application actually needs MCP. Provider packages such as `@effect/ai-openai` currently align at **4.1.2**. All remain unstable. [AI reference](https://effect.website/docs/v4/api/effect/ai/LanguageModel), [Toolkit source](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/ai/Toolkit.ts), [provider manifest](https://registry.npmjs.org/@effect/ai-openai/latest).

For durable agents, request tool definitions with `disableToolCallResolution: true`, persist the response, validate/approve calls, and execute each through its own activity. Otherwise automatic tool resolution can hide a side effect inside a model activity. Keep strict validation unless the application deliberately handles unknown calls. A bounded multi-turn loop, budgets, durable state, approvals, and safe side effects remain application responsibilities. [Resolution controls and implementation](https://github.com/Effect-TS/effect/blob/cb679e39cabeeadc5b40a5e20da311b9e4054a1b/packages/effect/src/ai/LanguageModel.ts).

## Alchemy: deployment and runtime must be evaluated separately

Current Alchemy is **2.0.0-beta.85**, with Effect **^4.1.0** peers; it is still beta. Its primary role is infrastructure as Effect: declaring/deploying resources and maintaining deployment state. That deployment state is not agent execution history. However, saying Alchemy is _only_ IaC is now incomplete: `alchemy/Workflows` supplies workflow registration/client helpers, and cloud packages implement Effect workflow engines. [Version and peers](https://github.com/alchemy-run/alchemy/blob/5bbe9aa4d8ea8975b47e488239c04afd68f2d54c/packages/alchemy/package.json), [workflow helpers](https://github.com/alchemy-run/alchemy/blob/5bbe9aa4d8ea8975b47e488239c04afd68f2d54c/packages/alchemy/src/Workflows.ts).

AWS uses `Lambda.WorkflowFunction` plus `DurableFunctionEngine`. Cloudflare has native-workflow and Durable Object engines. These are alternatives to the SQL cluster engine, with provider-specific lifetimes and signal/cancellation semantics; Alchemy is not required for a Postgres worker. AWS documentation notes execution timeouts include waits, signal delivery retries while a callback becomes available, and interrupting a busy step may require a provider stop without compensation. Assess the selected adapter's guarantees rather than assuming parity. Sources: [AWS runtime guide](https://alchemy.run/aws/compute/effect-workflows/), [Cloudflare native engine](https://github.com/alchemy-run/alchemy/blob/5bbe9aa4d8ea8975b47e488239c04afd68f2d54c/packages/cloudflare/src/Workflows/NativeEngine.ts), [Durable Object engine](https://github.com/alchemy-run/alchemy/blob/5bbe9aa4d8ea8975b47e488239c04afd68f2d54c/packages/cloudflare/src/Workflows/DurableObjectEngine.ts).

## What “Pi Durable” actually identifies

There is a concrete match: **Earendil's `@earendil-works/pi-durable`**, in `earendil-works/pi/packages/durable`; current source/npm version is **1.5.0**. Its README explicitly says **experimental; API changes without notice**. It is a durable agent harness over pi-ai and Chord, distinct from the interactive Pi coding agent. Rivet also integrates it as one actor per agent. Sources: [official package README](https://github.com/earendil-works/pi/blob/55a5c6914570e2ae31ca36297654483bbbf46883/packages/durable/README.md), [package manifest](https://github.com/earendil-works/pi/blob/55a5c6914570e2ae31ca36297654483bbbf46883/packages/durable/package.json), [Rivet integration](https://rivet.dev/agents/docs/pi/). This establishes the likely referent, not the user's unspoken intent.

It supplies conversations, durable task phases/checkpoints, registry/extensions, compaction, submission deduplication, and memory/SQLite/JSONL/IndexedDB storage. **One process owns a storage; no cross-process locking.** Postgres would require a custom backend, not a documented drop-in shared-worker mode. `Harness.open` plus `resume()` restarts pending work. Interrupted tools rerun only when explicitly `replay: "safe"`; unsafe calls yield interrupted results. Replay-safe external calls still need idempotency. Cancelling a wait does not cancel the work; `abort` is explicit. These contracts are in the [README's recovery, tools, abort, and storage sections](https://github.com/earendil-works/pi/blob/55a5c6914570e2ae31ca36297654483bbbf46883/packages/durable/README.md).

This is a credible alternative if the desired product is a conversation-first harness with built-in agent lifecycle. It introduces a second async/cancellation/state model alongside Effect. Integrating it here would require a scoped, interruptible adapter that forwards cancellation to Chord and closes/reports harness failures. Do not merely wrap the complete first-party application workflow in `Effect.promise`, and do not journal the same tool independently in Pi and Effect without choosing a single owner.

## Proposed module seam and acceptance criteria

**Design proposal, not an implemented specification:** an optional `apps/agent` owns one registered workflow and runtime composition. Expose a small application module interface: `start(requestKey, input) -> RunId`, `read(RunId) -> RunView`, `decide(RunId, approvalId, decision)`, `cancel(RunId)`. Each returns an Effect with explicit validation/storage/application failures. `RunView` should distinguish active work, approval wait, success, failure, and cancellation through application records; raw workflow polling alone is not a complete agent dashboard. HTTP/CLI callers cross this seam, while provider and workflow/cluster details stay inside the implementation. Avoid an interchangeable Pi/Effect/Alchemy engine interface until an actual second adapter is required.

Observable acceptance criteria for a later implementation:

- Repeating a request key admits one run; reusing it with incompatible input is rejected explicitly.
- Kill and restart the worker after a committed model/tool activity: recover the same run without repeating completed work. Also kill between external effect and result commit: the chosen deduplication/reconciliation strategy prevents a duplicate business outcome.
- An approval wait survives restart without holding a request open; its exact proposal is readable; stale, rejected, expired, and repeated decisions behave as specified.
- Disconnecting a client leaves admitted work running; explicit cancellation persists across restart, releases resources, and forwards cancellation where supported. Report cancellation as cooperative where the external system cannot stop.
- Transient model/storage failures obey a bounded policy; retry exhaustion and defects become visible. Limits stop runaway turns/spend; logs identify run/activity without exposing credentials.
- Run these against real file SQLite or Postgres as applicable. Add owner-loss tests only when multi-runner support is actually promised.

**Objections and alternatives:** an ordinary bounded Effect + AI operation is smaller when restart recovery and long waits are unnecessary. Persisted chat can suffice for user-driven continuation. A simple explicit database job/state machine may beat cluster machinery for one fixed task, but must own leases, retries, and crash windows. Pi Durable buys conversation lifecycle at the cost of a second runtime; Alchemy cloud adapters buy managed execution at the cost of hosting commitment and differing semantics. None justifies a mandatory agent layer in this starter.

Keep model credentials/provider defaults, tool registries, unrestricted shell/file tools, vector stores, RAG, MCP servers, multi-agent orchestration, approval UI, cloud/IaC defaults, and distributed-cluster operations **out of the base starter**. Add them only to an optional application with a concrete use case. Pin and compile the selected unstable modules before implementation; the source-backed compositions above are research, not a verified dependency lock or production readiness claim.
